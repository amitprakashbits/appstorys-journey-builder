R‑1

Journey setup

A short wizard defines who enters the journey and when, before the canvas opens.

R‑1.1
The user must choose a trigger type — segment-triggered or event-triggered. BUILT
Accept: switching type changes the fields shown below it.
R‑1.2
For an event trigger, the user selects a single trigger event. MUST
Accept: event chosen from the searchable, category-grouped catalog; only active events selectable.
R‑1.3
Audience is All users or specific cohorts; cohorts cannot be created here. BUILT
Accept: cohort droplist shows only active cohorts; empty state links out to the Cohorts flow.
R‑1.4
An estimated-reach figure updates live as trigger/audience change. SHOULD
Accept: the number recomputes without a page reload when inputs change.
R‑1.5
Setup state is preserved when moving to the canvas and back. MUST
Accept: "Back to setup" returns with every field intact.
R‑2

Canvas foundation

A free-form, top-down flow editor that fills the workspace.

R‑2.1
An empty journey shows a single "add first step" affordance and nothing else. BUILT
Accept: no Start/End nodes exist anywhere.
R‑2.2
Nodes are freely draggable to any position; the layout is the user's. BUILT
Accept: positions persist; snap-to-grid aligns to the grid but never forces a lane.
R‑2.3
The canvas pans and zooms smoothly and fills the area edge-to-edge. BUILT
Accept: space/middle-drag + trackpad pan; ⌘/Ctrl-scroll + pinch zoom; fit-view on load; no white gutter.
R‑2.4
A bottom toolbar provides zoom, fit, snap toggle, tidy-up (auto-layout), undo/redo, and shortcuts. A minimap sits bottom-right. BUILT
Accept: tidy-up arranges the flow into a clean top-down tree; toolbar and minimap never overlap at 1024px.
R‑2.5
Performance must stay smooth at ~100 nodes. MUST
Accept: no jank on pan/zoom; cards don't re-render on viewport change.
R‑3

Nodes

R‑3.1
Each node card shows its type (icon + name), an editable title, and the 2–3 highest-signal config values. BUILT
Accept: values update live on the card after an edit; card never grows unbounded.
R‑3.2
The trigger config appears as a badge on the first node; entry is the node with no incoming connection. BUILT
Accept: no separate Start node; the entry node cannot receive an incoming connection.
R‑3.3
A node missing required config shows a clear "needs setup" indicator with the reason. BUILT
Accept: a red "!" badge appears; hovering states the missing field.
R‑3.4
A terminal node (no outgoing connection on a port) is visually indicated. BUILT
Accept: the unconnected output port shows a subtle end cap.
R‑3.5
Selecting/hovering a node reveals a toolbar: Edit, Duplicate, Send test, Delete. BUILT
Accept: each acts on that node; multi-select via shift-click and marquee.
R‑4

Connections

R‑4.1
Users connect nodes by dragging from an output port to another node's input port. BUILT
Accept: a live line follows the cursor; release on a port connects; ports have a forgiving hit area.
R‑4.2
Dropping a connection on empty canvas opens the palette and creates the node + connection in one action. BUILT
Accept: picking a type places a connected node at the drop point.
R‑4.3
Hovering a connection reveals a "+" to insert a node inline; palette rows can also be dropped onto a connection. BUILT
Accept: inserting rewires the two ends automatically.
R‑4.4
A connection can be re-wired by grabbing its end, or detached by dropping on empty canvas. BUILT
Accept: both are undo-able.
R‑4.5
Invalid connections are rejected with a reason. MUST
Accept: blocks self-loops, connections into the entry node, duplicates, and cycles; a toast explains why.
R‑4.6
Branching nodes fan out into labelled outputs that connect independently. BUILT
Accept: Yes/No (conditions) or per-variant (splits) labels ride on the connection.
R‑4.7
Connections show an animated flow on hover to make the wiring feel live. BUILT
Accept: brand-colour packets travel the hovered connection; disabled under reduced-motion.
R‑5

Add-node palette

R‑5.1
A single palette opens from the empty-canvas add, an edge "+", or a connection-drop. BUILT
Accept: one component, three entry points.
R‑5.2
The palette is search-first, grouped by family with live counts. BUILT
Accept: search filters across all families; arrow keys + Enter place a node.
R‑5.3
Rows can be clicked to add, or dragged onto the canvas / onto a connection to insert. BUILT
Accept: drop point becomes the node position; a preview follows the cursor.
R‑5.4
Selecting a campaign type routes into the campaign import/create step (see R‑9). SHOULD
Accept: import an existing campaign or create a new one of that type.
R‑6

Node editor

R‑6.1
Every node type opens a working editor — no dead nodes. BUILT
Accept: double-click or the Edit action opens a right-side sheet with a type-specific form.
R‑6.2
The editor header shows a READY / NEEDS-SETUP status and an editable title. BUILT
Accept: status reflects the current (draft) config in real time.
R‑6.3
A live preview shows what the canvas card will become as the user edits. BUILT
Accept: preview updates before saving.
R‑6.4
Save is disabled until there are changes; saving reflects on the card immediately. BUILT
Accept: edits are undo-able.
R‑6.5
Closing with unsaved changes asks to discard or keep editing. BUILT
Accept: drafts never leak between nodes.
R‑6.6
Campaign content is edited via a hand-off, not in the sheet. MUST
Accept: "Send test" and an "edit content" hand-off open from the sheet; no campaign-content fields inside it.

Adding a new node type must not be possible without its card, editor, validation, and default config. BUILT

R‑8

Conditions (Event / Attribute)

A shared condition builder used wherever a node branches on user behaviour or properties.

R‑8.1
A condition is either an Event condition or an Attribute condition, chosen by a tab. BUILT
Accept: switching the tab swaps the field set.
R‑8.2
Event mode supports verb, event, a count operator + count, a time window, and event-property filters. BUILT
Accept: "has executed <event> ≥ N times in the last <period>" with additional property rows.
R‑8.3
Attribute mode supports attribute, operator, and value. BUILT
Accept: operators and value input adapt to the attribute type (number / enum / boolean / string).
R‑8.4
Multiple conditions can be stacked. BUILT
Accept: "Add another filter condition" appends a card.
R‑8.5
The same builder is used everywhere a condition is defined. SHOULD
Accept: Conditional Split, Check User Attribute, Has done event use it today; the entry trigger + exit + goal should adopt it.
R‑9

Campaign selection

R‑9.1
Every campaign node lets the user import an existing campaign or create a new one of that type. BUILT
Accept: the same picker across all 12 campaign types.
R‑9.2
Import shows a searchable list of campaigns with name, date, and status, and supports select/select-all. BUILT
Accept: "Import" is disabled until a campaign is selected.
R‑9.3
"Create a new <type> campaign" opens the campaign builder for that type. SHOULD
Accept: returns to the journey builder afterwards.
R‑10

Audience & events

R‑10.1
Cohorts are never created inside the Journey Builder. MUST
Accept: the cohort droplist is read-only selection; creation redirects to the Cohorts flow.
R‑10.2
The cohort droplist shows only active cohorts. BUILT
Accept: archived/draft cohorts are excluded.
R‑10.3
All event selection uses one shared event picker. BUILT
Accept: searchable, grouped by category; one component across goal, trigger, and conditions.
R‑10.4
Events expose their attributes for filtering. BUILT
Accept: selecting an event enables attribute-based filters with type-aware operators.
R‑11

Validation & publish

R‑11.1
Publish is blocked with a clear reason when the journey is incomplete. MUST
Accept: requires ≥ 1 node, a configured trigger event, and no orphaned branch (every branch output must be connected).
R‑11.2
Each node reports its own readiness. BUILT
Accept: readiness drives the node "!" badge and the editor status pill consistently.
R‑11.3
Draft can be saved at any time. MUST
Accept: saving a draft does not run publish validation.
R‑12

History & keyboard

R‑12.1
Undo/redo covers add, insert, connect, move, delete, duplicate, and edits. BUILT
Accept: bounded history (≥ 50 steps); a drag is one undo step, not many.
R‑12.2
Keyboard accelerators exist for common actions. BUILT
Accept: Delete/Backspace delete; ⌘/Ctrl+D duplicate; ⌘/Ctrl+Z and ⇧⌘Z undo/redo; ⌘/Ctrl+A select all; arrows nudge (⇧ = larger). All discoverable via a "?" popover.
R‑12.3
Every action achievable by keyboard is also achievable by mouse. MUST
Accept: keyboard is an accelerator, never the only path.
R‑13

Persistence & integrations

R‑13.1
The full journey (setup + flow graph) must save and reload without loss. MUST
Accept: reloading a saved journey restores nodes, connections, positions, config, and the entry point. SHOULD (persistence layer not yet built).
R‑13.2
Editing a campaign in another tab is reflected in the builder on refresh/refocus. SHOULD
Accept: node campaign summaries refetch on window focus and via a manual refresh; an "updated" timestamp shows.
R‑13.3
Events, campaigns, cohorts, and reach come from live data. MUST
Accept: the current mock sources are replaced by APIs; UI contracts stay unchanged.
R‑14

Non-functional

R‑14.1
The builder follows the AppStorys design system throughout. BUILT
Accept: brand colours, spacing, and Poppins; no off-token colours.
R‑14.2
Motion respects reduced-motion preferences. BUILT
Accept: flow animation, hover lifts, and layout animation are disabled under reduced-motion.
R‑14.3
Controls are keyboard-focusable with a visible focus state. SHOULD
Accept: palette, editor, and toolbar are operable without a mouse.
